检索增强生成（RAG）是大模型落地最常见的模式：把外部知识检索进来，让模型基于事实回答。但"能跑"和"好用"之间，隔着分块、检索、重排、压缩一连串工程细节。本文给出一份可直接落地的清单。

## RAG 的标准链路

一条完整的 RAG 链路包含四个阶段：**切块 → 检索 → 重排 → 生成**。每个阶段都有可以优化的空间。

```mermaid
graph LR
  A[文档] --> B[分块 Chunking]
  B --> C[向量化+入库]
  C --> D[检索 Top-K]
  D --> E[重排 Rerank]
  E --> F[上下文压缩]
  F --> G[LLM 生成]
```

## 1. 分块策略

分块决定了检索的粒度，是 RAG 效果的地基。

- **定长分块**：简单粗暴，但容易切断语义。适合快速起步。
- **按语义分块**：以段落或标题为边界，保留语义完整。推荐作为默认。
- **父子分块**：检索用小块，召回后返回其所属大块，兼顾精准与上下文。生产环境首选。

> 经验值：中文 chunk 建议 300-500 字，重叠 50 字，避免关键信息被切断在边界。

## 2. 向量检索

向量检索负责从海量 chunk 中召回相关候选。混合检索（向量 + 关键词 BM25）通常优于纯向量。

- 纯向量擅长语义近似，但专有名词、ID、代码符号容易漏。
- BM25 擅长精确匹配，补齐向量短板。
- 两者分数融合（RRF）是目前最稳的工业实践。

## 3. 重排

召回的 Top-K 里混有噪声，重排模型（cross-encoder）对 query 与每个候选做精细打分，把真正相关的提到前面。这一步往往带来最大的效果提升。

## 4. 上下文压缩

塞给 LLM 的不是越多越好。冗余上下文会稀释注意力，甚至触发"中间遗忘"。建议：

- 重排后只取 Top 3-5 个 chunk。
- 对每个 chunk 做摘要压缩，只保留与 query 相关的句子。
- 总 token 控制在模型上下文的 1/3 以内。

## 工程清单

落地一个生产级 RAG，按这份清单逐项检查：

1. 分块是否保留语义完整（父子分块）？
2. 是否启用混合检索（向量 + BM25）？
3. 是否接入了重排模型？
4. 上下文是否经过压缩与去重？
5. 是否对最终答案做了引用标注（可溯源）？
6. 是否有失败兜底（检索为空时的标准回复）？

RAG 不神秘，它是一连串可调试的工程决策。把每一步都做对，效果自然就稳。
